Status: planned
# Translation / i18n Plan

Goal: translate everything the admin UI shows — column labels, resource titles,
sidebar entries, enum option labels, UI chrome, validation messages — **server
side**. The frontend never owns a translation catalogue. It sends
`Accept-Language`, the API answers in that language.

Modelled on the existing shared-enum mechanism (`crouton.enums.json` →
`enum-registry` → `injectEnumValues`), which already proves the pattern:
one project-level JSON file, generated/merged by the CLI, loaded once by the
API, injected into columns at config-build time.

---

## 1. Decisions

| Question | Decision |
| --- | --- |
| File layout | `translations/<lang>.json`, one file per language, dir configurable |
| Key shape | **Nested per resource** — `resources.group.columns.name` |
| Language transport | `Accept-Language` (standard q-value negotiation) |
| Fallback chain | requested language → default language file → `resource.json` `label` → `labelFromId(id)` |
| Default language | `en` (configurable) |
| Generation | `crouton-cli`, folded into `crouton update resources` + a standalone command |
| Scope | column labels, resource/sub-resource titles, sidebar (+ groups), enum option labels, UI chrome, validation messages |

---

## 2. File format

`crouton.json` gains an `i18n` block:

```json
{
  "title": "My app",
  "resourcesDir": "resources",
  "enumsFile": "crouton.enums.json",
  "i18n": {
    "defaultLanguage": "en",
    "languages": ["en", "nl", "fr"],
    "translationsDir": "translations"
  }
}
```

`translations/nl.json`:

```json
{
  "app": {
    "title": "Mijn applicatie"
  },
  "sidebarGroups": {
    "metadata": "Metadata"
  },
  "resources": {
    "group": {
      "title": "Groepen",
      "sidebar": "Groepen",
      "columns": {
        "name": "Naam",
        "description": "Beschrijving",
        "author_name": "Auteursnaam"
      },
      "actions": {
        "publish": "Publiceren"
      },
      "subResources": {
        "members": {
          "title": "Leden",
          "columns": { "role": "Rol" }
        }
      }
    }
  },
  "enums": {
    "Status": {
      "ACTIVE": "Actief",
      "ARCHIVED": "Gearchiveerd"
    }
  },
  "ui": {
    "actions": { "save": "Opslaan", "cancel": "Annuleren", "delete": "Verwijderen" },
    "table": { "empty": "Geen resultaten", "of": "van" }
  },
  "validation": {
    "required": "{field} is verplicht",
    "invalid_type": "{field} heeft een ongeldig type"
  }
}
```

Notes:

- `resources.<name>` is keyed on `resource.json` `name` (the same key the
  registry and `formDef.id` use), not on `route` — routes can change without
  breaking translations.
- Column keys are column **ids**, including the virtual ids generated by
  `extend` (`author_name`), so `expandExtendColumns` output is translatable.
- Every section is optional. An empty `{}` file is valid and means "fall back
  everywhere".
- The `en.json` file is a real file, not implicit — it is the curated base of
  the fallback chain, generated with `labelFromId`/`resource.json` labels.

## 4. Core: translator and negotiation

```ts
// translator.ts
export type Translator = (path: string, fallback?: string) => string;

export const createTranslator = (
  bundles: Record<string, TranslationBundle>,
  language: string,
  defaultLanguage = 'en',
): Translator => { /* walk requested → default → fallback arg */ };
```

Resolution order for one lookup, e.g. `resources.group.columns.name`:

1. `bundles[language]` at that path
2. `bundles[defaultLanguage]` at that path
3. the `fallback` argument — which callers pass as the existing
   `column.label` from `resource.json`
4. `labelFromId(column.id)` — already the last resort today

Empty strings count as "missing" so a placeholder key never blanks a header.

```ts
// negotiate.ts
resolveLanguage('nl-BE,nl;q=0.9,en;q=0.7', ['en', 'nl', 'fr'], 'en') // → 'nl'
```

Parses q-values, matches exact then base tag (`nl-BE` → `nl`), falls back to
the default. Case-insensitive. `*` → default.

## 5. Codegen + CLI generation

`crouton-codegen/src/translations.ts` mirrors `enum-registry.ts` one-for-one:

```ts
buildTranslationBundle(resources: ResourceJson[], enums: EnumRegistry): TranslationBundle
mergeTranslationBundle(existing, generated): TranslationBundle   // hand edits win, never dropped
findStaleKeys(existing, generated): string[]                      // keys no longer backed by a column
serializeTranslationBundle(bundle): string                        // stable key order + trailing newline
```

- `buildTranslationBundle` seeds every value from the current source of truth:
  a column's `label`, else `labelFromId(id)`; a resource's `title ?? tag`; an
  enum member's label from `crouton.enums.json`.
- `mergeTranslationBundle` adds new keys, preserves existing values and key
  order. Same contract as `mergeEnumRegistry` — the file is hand-editable and
  regeneration is safe.
- For a non-default language, new keys are seeded **empty** (`""`) rather than
  with the English label, so untranslated keys are visible in a diff and fall
  back cleanly. `--seed-from-default` fills them with the default-language
  value instead, for translators who prefer to overwrite.

CLI surface:

```
crouton translations init                 # create translations/<lang>.json for every configured language
crouton translations update               # regenerate + merge (alias: crouton update translations)
  --lang nl,fr                            # limit to some languages
  --prune                                 # remove keys with no backing column/enum (reports first)
  --dry-run
  -y, --yes
```

`crouton update resources` also refreshes translations in the same preview /
confirm / write pass it already uses for `crouton.enums.json` (`runner.ts`
~line 397–483): compute the merged bundle per language, add
`~ translations/nl.json (12 new key(s))` lines to the preview, include them in
the file count, write them after `commit()`. So the normal database-sync flow
keeps the translation files in step with newly-introspected columns without a
second command.

## 6. API: where translation is applied

The important observation from the current code: `json_schema` titles come from
`col.label ?? col.id` in `view.builder.ts` (lines 68, 419, 433), and views are
built **once at load time** inside `fromJson`. So translating a column label
before views are built gives translated table headers, form labels, view labels
and filter labels for free — no post-processing of compiled JSON Schema.

### 6.1 Localized resource cache

```ts
// localize-resource.ts
export const localizeResource = (config: Resource, t: Translator): Resource
```

Steps:

1. Translate `title` / `tag` / `sidebar.label`.
2. Map columns → new array with `label` replaced (fallback = existing label).
3. Translate `fieldInput.options.values[].label` (enum options).
4. **Rebuild views** from the translated columns.
5. Rebuild `valueLabelColumns` from the translated columns (read-path envelope).
6. Same treatment for each `subResources[]` entry (title, columns, views,
   `valueLabelColumns`).
7. Translate row/table action labels.
8. Leave everything else — `definition`, `hooks`, `repository`, `include`,
   `lookup`, URIs — untouched by identity, so behaviour is unchanged.

**Refactor to avoid duplication:** extract the "columns → views" block of
`fromJson` (`json-adapter.ts` lines ~100–115, including the calculated-column
injection) into an exported `buildResourceViews(json, schema, columns, calculatedColumns)`.
`fromJson` and `localizeResource` both call it. One implementation, no drift.

`ResourceConfigRegistry` gains a per-language memo:

```ts
getByRoute(route: string, language?: string): Promise<Resource | undefined>
getAll(language?: string): Promise<Resource[]>
```

backed by `Map<language, Map<route, Resource>>`, filled lazily on first request
per language and cleared whenever the underlying configs reload (dev mode
already reloads per request — localization happens after the fresh load, and
the memo is keyed on the reload generation so dev edits are not served stale).

Cost: one extra `Resource` + views per language per resource, built once.
For 3 languages × 40 resources that is negligible; it is bounded by
`i18n.languages`, so an unknown `Accept-Language` can never grow the cache.

### 6.2 Request language

A `LanguageInterceptor` (global, registered by `CroutonApiModule`):

1. `resolveLanguage(req.headers['accept-language'], registry.languages, registry.default)`
2. stores it in an `AsyncLocalStorage` (`language.context.ts`)
3. sets `Vary: Accept-Language` and `Content-Language: <resolved>` on the response

`AsyncLocalStorage` rather than threading a parameter, because the read path
(`read.repository.ts` → `applyValueLabelColumns`, and `hooks.apply.ts`) is
several layers deep and every signature would otherwise change. A
`getRequestLanguage()` helper returns the default outside a request scope, so
tests and CLI usage keep working unchanged.

### 6.3 Endpoints touched

| Endpoint | Change |
| --- | --- |
| `GET /<route>/schemas` | build payload from the localized config |
| `GET /<route>/<child>/schemas` | idem for sub-resources |
| `GET /<route>/definition` | idem |
| `GET /<route>/resource.json` | idem |
| `GET /_app/layout` | localized sidebar + group labels + app title; adds `i18n: { languages, default, current }` and the `ui` dictionary |
| `GET /_app/translations` *(new)* | `ui` + `validation` dictionary only, for a client that wants it separately |
| `GET /_app/status` | new panel: languages found, key counts, missing/stale per language |
| read endpoints (`findAll` / `findOne`) | `{ value, label }` envelope uses the localized option list |

Every one of these gets `Vary: Accept-Language` so a CDN or browser cache
cannot serve a Dutch schema to a French client.

The dev-only editor endpoints (`resource-columns`, `resource-json-raw`,
`PATCH /resource.json`) intentionally serve **untranslated** data — they edit
`resource.json`, so they must show what is on disk.

### 6.4 Enum labels on the data path

`buildValueLabelColumns(columns)` snapshots `{value,label}[]` per column at load
time, and `applyValueLabelColumns` uses it on every read. Because
`localizeResource` rebuilds `valueLabelColumns` from translated columns, the
repository only needs the localized config for the current request:

- `read.repository` / `custom-repository.adapter` / `hooks.apply` resolve their
  value-label columns through a small `resolveValueLabelColumns(config)` helper
  that consults `getRequestLanguage()` instead of reading `config.valueLabelColumns`
  directly.
- Write path (`normalizeValueLabels`) is unaffected — it discards labels and
  keeps the scalar, in any language.

**Documented limitation:** sorting and filtering on an enum column operate on
the stored scalar, not the translated label (`sanitizeValueLabelSort` already
strips label sorts). Translating does not change ordering semantics.

### 6.5 Validation messages

`CroutonValidationExceptionFilter` maps zod issue codes to
`validation.<code>` keys with `{field}` interpolation, where `field` is the
already-translated column label. Unmapped codes keep the current message, so
this is additive and cannot make an error less informative.

## 7. Frontend: provider + dropdown, no catalogue

Same shape as `useApi.ts` (module-level singleton + `configure*`), so it reads
as existing crouton API.

```ts
// useLanguage.ts
configureLanguage({
  languages: ['en', 'nl', 'fr'],   // overridden by /_app/layout
  defaultLanguage: 'en',
  initial: 'nl',                   // optional; else persisted → navigator → default
  persist: true,                   // localStorage key `crouton.language`
});

const { language, languages, setLanguage, t } = useLanguage();
```

- `installLanguageHeader(api)` adds an axios request interceptor that sets
  `Accept-Language: <current>` on every call. Called from `CroutonPlugin` /
  `useCrouton().init(api)` so consumers get it for free; a consumer with its own
  axios instance can call it directly.
- `setLanguage(lang)` → updates the ref → `refreshLayout()` and re-resolves the
  active view's `FormDef`.
- **`FormDefCache` is keyed by `${language}:${uri}`** instead of `uri`, so
  switching back to a previously used language is instant and no cross-language
  bleed is possible. `invalidate(formId)` clears that id across all languages.
- `t('ui.actions.save')` is a **dictionary lookup only** — the dictionary comes
  from `/_app/layout`. No i18n library, no bundled strings, and the frontend
  still has no knowledge of how translation is resolved.

`LanguageSelect.vue` — default dropdown, props in a sibling
`LanguageSelect.properties.ts` (runtime object syntax, per `CLAUDE.md`), bound
to `useLanguage()`. Rendered in `AdminView.vue`'s header when the backend
reports more than one language; a `hideLanguageSelect` option on `AppConfig`
opts out, and consumers can drop in their own control since `setLanguage` is
public.

## 8. Phases

Each phase is independently shippable and, until phase 2, a pure no-op for
existing projects.

| # | Phase | Contents |
| --- | --- | --- |
| 0 | Config + core | `i18n` in `CroutonConfigSchema`, `Translations.schema`, `translator`, `negotiate` + unit tests. No behaviour change. |
| 1 | Generation | codegen `translations.ts`, `crouton translations init/update`, wire into `crouton update resources`. Files exist, nothing consumes them. |
| 2 | API labels | loader + registry, `buildResourceViews` extraction, `localizeResource`, per-language registry memo, `LanguageInterceptor`, `Vary`. Schemas/definitions/layout become translatable. |
| 3 | Enum + data path | option labels + `valueLabelColumns` per language, `resolveValueLabelColumns` in read paths. |
| 4 | UI + validation | `ui` / `validation` sections, `/_app/translations`, validation filter mapping. |
| 5 | Frontend | `useLanguage`, axios header interceptor, locale-keyed `FormDefCache`, `LanguageSelect`, `AdminView` wiring. |
| 6 | Docs + status | `docs/guide/translations.md`, status-page panel, `CHANGELOG` / `RELEASE_NOTES`. |

## 9. Tests

- `negotiate`: q-values, base-tag match, `*`, unknown, empty header.
- `translator`: full fallback chain, empty-string treated as missing,
  missing bundle, unknown path.
- `mergeTranslationBundle`: hand edits preserved, new keys appended, key order
  stable, `findStaleKeys` after a column rename.
- `localizeResource`: table/form/view/filter titles per language; untranslated
  key falls back to the `resource.json` label; `extend` virtual columns;
  sub-resource views; identity of `definition`/`hooks`/`repository`.
- `buildResourceViews` extraction: `fromJson` output byte-identical before/after
  the refactor (regression guard).
- e2e per endpoint: `Accept-Language: nl` vs `fr` vs absent vs garbage;
  `Vary`/`Content-Language` present.
- read path: `{ value, label }` envelope localized; sort/filter unchanged.
- frontend: cache keyed per language; interceptor sets the header;
  `setLanguage` triggers layout refresh.

## 10. Risks and open points

- **Key drift.** Renaming a column id orphans its translations silently.
  Mitigated by `findStaleKeys` in the CLI preview and the status-page panel;
  `--prune` removes them only after showing the list.
- **Boot/memory.** Bounded by `i18n.languages` × resources, built lazily and
  memoized. Worth a log line with the localized-config count at startup.
- **Dev-mode reload.** `IS_DEV` rebuilds config per request; the per-language
  memo must be keyed on the reload generation or it will serve stale labels
  right after a `resource.json` edit. Explicit test.
- **Caching.** Any reverse proxy in front of crouton must honour
  `Vary: Accept-Language`. Called out in the docs.
- **No translated search.** The DB stores scalars, so full-text search and
  filtering never see translated labels. Documented, not solved.
- **Content vs chrome.** This plan translates *metadata*, not row data.
  Translating record values (a `Group.name` that differs per language) is a
  data-model question — separate proposal.
- **`labelFromId` lowercases.** `labelFromId('fieldLabel')` → `"Field label"`.
  Generated `en.json` inherits that casing; hand-edit or set `label` in
  `resource.json` if a different casing is wanted. Not changed here, since it
  would move every existing label.

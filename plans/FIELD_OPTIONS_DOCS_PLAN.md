# Field Input Options Docs (generated from Zod) — Plan

## Goal

A docs section that documents every `fieldInput.options` key per type (`string`, `select`,
`autocomplete`, …), **generated from the Zod schemas** in
`packages/crouton-core/src/lib/resource/field-input/` so the docs can never drift from the code.

## Why not JSDoc

Zod schemas are runtime values; JSDoc comments are erased at compile time, so reading them needs a
TS-AST parser (ts-morph) over the source — fragile, and it duplicates what Zod already supports.
**Zod v4 has first-class metadata**: `.meta({...})` (and `.describe()`, which is sugar for
`meta.description`). It is stored in `z.globalRegistry` and **emitted by `z.toJSONSchema()`**, which we
already run. So one annotation feeds three outputs:

1. the docs pages (this plan),
2. the published `*.field-input.schema.json` → hover docs/autocomplete in VS Code while editing
   `resource.json` (free win),
3. `z.infer` types stay unchanged.

Decision: **document with `.meta()`, not JSDoc.**

## Current state (what we build on)

- `base.options.ts` + `types/*.options.ts` — Zod schemas; only a few keys have `.describe()`.
- `registry.ts` — `fieldInputRegistry` maps `type → { options, schemaFile }` (aliases such as
  `Integer`→number, `dateTime`→date share a schema).
- `crouton-core/scripts/gen-resource-schema.mjs` already loops the registry and writes
  `<type>.field-input.schema.json` (committed + drift-checked + copied to `docs/.vuepress/public/schema/v1`).
- `docs/guide/resource/field-input-types.md` — **hand-written** option tables that have already drifted:
  documents `colspan` as 1–12 and a `width` enum the schema doesn't express, omits `styles`, and most
  per-type options (`clearable`, `storeValue`, `skipAuth`, …) are undocumented.

## Step 1 — Metadata convention in the schemas

Use a small typed helper so every option carries the same shape:

```ts
// field-input/option-meta.ts
export type FieldOptionMeta = {
  description: string;          // required: one sentence
  examples?: unknown[];         // emitted as JSON Schema `examples`
  default?: unknown;            // documented default (not applied) – or use .default()
  deprecated?: boolean;
  since?: string;               // crouton version, docs-only
};
export const opt = <T extends z.ZodType>(schema: T, meta: FieldOptionMeta) => schema.meta(meta);
```

```ts
// base.options.ts
export const BaseOptionsSchema = z.object({
  label: opt(z.string().optional(), { description: 'Override the field label' }),
  colspan: opt(z.number().optional(), {
    description: 'Grid column span (1–12)', examples: [6, 12],
  }),
  width: opt(z.string().optional(), {
    description: 'Named width (xs, sm, md, lg, xl, full) or any CSS value', examples: ['md', '240px'],
  }),
  // …
}).catchall(z.unknown()).meta({ title: 'Base options', description: 'Accepted by every field input type' });
```

- Put `.meta()` **after** `.optional()` so it attaches to the property as JSON Schema sees it.
- Add `title` + `description` on each `XxxOptionsSchema` (used as the page intro).
- For unions (`AutocompleteOptionsSchema`) put `title` on each variant (Inline / Remote / Resource).
- Arrow functions only (CLAUDE.md).

## Step 2 — Generator: Zod → Markdown

New script `crouton-core/scripts/gen-field-input-docs.mjs`, called from the same tsup `onSuccess` as
`gen-resource-schema.mjs` (it imports from `../dist/index.js` the same way).

For each **unique** `schemaFile` in `fieldInputRegistry`:

1. `z.toJSONSchema(def.options, { target: 'draft-7', io: 'input', unrepresentable: 'any' })`.
2. Split properties into **own** vs **inherited**: keys present in `BaseOptionsSchema.shape` are
   inherited → render once on a shared "Common options" partial and link to it.
3. Render a table: `Option | Type | Required | Default | Description | Example`.
   - type from JSON Schema (`type`, `enum`, `anyOf`, `items`) via a small `formatType()` helper.
   - `required` from the schema's `required` array.
4. Unions (`anyOf` at the root) → one sub-table per variant, using the variant `title`.
5. List the registry aliases that use this schema (`number` ← `number`, `Integer`).
6. Write `docs/guide/resource/field-inputs/_generated/<schemaFile>.md` with a
   `<!-- generated by gen-field-input-docs.mjs — do not edit -->` header.

Walking the JSON Schema output (not Zod internals) keeps the generator stable across Zod updates and
guarantees the docs show exactly what the published `$schema` validates.

## Step 3 — Docs pages (hand-written prose + generated tables)

```
docs/guide/resource/field-inputs/
  index.md               ← overview + type table (moved from field-input-types.md)
  common-options.md      ← prose + @include(_generated/base.md)
  string.md              ← prose/examples + @include(_generated/string.md)
  select.md, autocomplete.md, …
  _generated/*.md        ← generator output (committed)
```

- Enable the theme's include: `hopeTheme({ markdown: { include: true } })` → `<!-- @include: ./_generated/string.md -->`.
- Hand-written files hold **only** narrative + JSON examples; option tables come exclusively from the include.
- `_`-prefixed files are already hidden by the menu/sidebar convention (check `tools/doc/vuepress.mjs`
  excludes `_generated`; add it to `EXCLUDE_ALWAYS` if not).
- Replace `field-input-types.md` with a redirect/link to the new index.

## Step 4 — Keep it honest (CI)

- Add `_generated/*.md` to the existing drift check used for the committed JSON schemas
  (build, then `git diff --exit-code`).
- Unit test `field-input-meta.spec.ts`: every property of every registered options schema has a
  non-empty `description` → a new option without docs fails the test.
- Optional: a stub-page check — every unique `schemaFile` has a `field-inputs/<schemaFile>.md`.

## Step 5 — Custom/registered types (optional)

Apps call `registerFieldInputType()`. Expose the generator as a function in `crouton-codegen`
(`renderFieldOptionsMarkdown(schema)`) so a consuming app can generate docs for its own types.
Must stay in codegen (Node-only), not core.

## Open decisions

1. `colspan`/`width`: document the constraint only via `.meta()`, or also enforce it
   (`z.number().int().min(1).max(12)`, `z.union([z.enum([...]), z.string()])`)? Enforcing is a
   validation change → may reject existing `resource.json` files.
2. Typo `mutliSelect` in the registry — keep as-is (documented alias) or add `multiSelect` + migrate?
3. Generated markdown (recommended: searchable, reviewable diffs, matches existing drift-check pattern)
   vs a live Vue component (`<FieldOptionsTable type="string" />`) that calls `z.toJSONSchema` in the
   browser — zero build step, but tables aren't in the search index and the drift check doesn't apply.

## Order of work

1. `opt()` helper + metadata on `base.options.ts` and `string.options.ts` (pilot).
2. Generator script + `_generated/base.md`, `_generated/string.md`.
3. `common-options.md` + `string.md` pages, include enabled, sidebar check.
4. Roll metadata out to the remaining 12 option files.
5. Meta-coverage test + drift check.

# Crouton Prisma Generator Plan (`crouton-prisma`)

## Goal

Collapse the two per-datasource generator blocks:

```prisma
generator client {
  provider        = "prisma-client-js"
  output          = "../../generated/default/client"
  previewFeatures = ["partialIndexes"]
}

generator zod {
  provider                         = "zod-prisma-types"
  output                           = "../../generated/default/types/src"
  addInputTypeValidation           = "false"
  createInputTypes                 = "false"
  createModelTypes                 = "true"
  createOptionalDefaultValuesTypes = "false"
  createRelationValuesTypes        = "true"
  useMultipleFiles                 = "true"
  writeBarrelFiles                 = "true"
}
```

into (the `client` block stays; only the `zod` block is replaced):

```prisma
generator client {
  provider        = "prisma-client-js"
  output          = "../../generated/default/client"
  previewFeatures = ["partialIndexes"]
}

generator crouton {
  provider  = "crouton-prisma"
  zodOutput = "../../generated/default/types/src"
}
```

A plain `prisma generate` then runs both generators; the crouton one does, in order:
1. **normalize** the schema (relation-field renames) — first, so zod sees clean names
2. `zod-prisma-types` generation into `zodOutput`
3. the remaining **no-prompt** custom crouton codegen (fixZodImports, enum registry, zod barrel cleanup)

…so we no longer post-process zod in the CLI's `pullAndGenerate` pipeline — the generator owns it. The Prisma client stays its own block and is generated by Prisma as usual.

---

## Key facts established from the codebase

- A Prisma generator is an npm package whose `bin` name equals the `provider` string, driven over JSON-RPC by `@prisma/generator-helper` (`generatorHandler` with `onManifest` + `onGenerate`). `onGenerate` receives `GeneratorOptions` = full DMMF, datasources, this generator's config (incl. `output` + arbitrary options), the schema SDL string (`datamodel`), and `otherGenerators`.
- Today the post-processing lives in `packages/crouton-codegen/src/prisma-shell.ts` → `pullAndGenerate()`:
  `backup → dbPull → prismaCaseFormat → normalizeSchema → prismaGenerate → fixZodImports`.
  - `normalizeSchema()` rewrites relation **field names in `schema.prisma` text** using a sibling `normalize-schema.json`. **This mutates the schema and must run *before* generation** or zod output keeps the ugly names.
  - `fixZodImports()` injects a missing `import { z } from 'zod'` across the zod output dir — this is a true post-generate step.
- The schema template that emits the two blocks is `packages/crouton-codegen/src/datasource-scaffold.ts` (`buildDatasourceFiles`, prisma branch). It also writes `data-source.json` carrying `zodOutput`, `clientOutput`, `generatedTypesImport`, `prismaConfig`.
- `data-source.json` fields are consumed by the CLI: `zodOutput` → `pullAndGenerate.zodOutputDir` / `fixZodImports` (`update/runner.ts`), `generatedTypesImport` → resource `schema.ts` import, `clientOutput` → datasource `index.ts` runtime import.
- `crouton-codegen` is `private: true` and imports `crouton-core`; the DMMF→model normalizer (`introspect.ts` `dmmfToDbModels`), `fixZodImports`, `normalizeSchema`, `buildEnumRegistry` all already live there and are reusable.
- The crouton workspace itself does **not** install prisma / zod-prisma-types / `@prisma/generator-helper` — those live in the **consumer** project (e.g. `examples/book-collection/apps/backend`). The generator runs in the consumer, so it must ship its own runtime deps and bundle any crouton logic it needs.
- resource.json / schema.ts generation is the **decision-driven** `update resources` flow (introspect → classify → diff → resolve → apply). It is interactive and must **not** move into a headless `prisma generate`.

## Open decisions (confirm before build)

1. **~~Where does field-name `normalizeSchema` run?~~ — RESOLVED.**
   Normalize runs **first, inside the generator, before zod** (so zod picks up the clean relation names). Order becomes `normalize → zod (+ client) → custom`. Mechanics: the generator applies the `normalize-schema.json` renames to the schema SDL string, writes that normalized SDL into the temp schema it feeds the sub-generators, and writes the normalized SDL back to the real `schema.prisma` so source and generated output stay in sync. The CLI's pre-generate `normalizeSchema` call is therefore removed from `pullAndGenerate` (the generator owns it).
2. **~~Does `crouton` also drive `prisma-client-js`?~~ — RESOLVED.** No. The `generator client` block stays. `crouton` owns only normalize + zod + the no-prompt custom steps. **Consequence (see Caveat below):** in one `prisma generate` pass Prisma parses the DMMF once and hands the *same* (pre-crouton) DMMF to the client block, so the client would emit un-normalized relation names unless the schema on disk is already normalized before the pass.
3. **~~Which "other custom logic" belongs in the generator?~~ — RESOLVED.** Only the no-prompt, deterministic steps: `fixZodImports`, enum-registry emit, zod barrel/`index.ts` cleanup. resource.json / schema.ts generation stays in the decision-driven `update resources` flow and does **not** move into `prisma generate`.

## Proposed architecture

### New package: `packages/crouton-prisma` (`@ghentcdh/crouton-prisma`, published)

- `package.json`: `"bin": { "crouton-prisma": "./dist/generator.js" }` so `provider = "crouton-prisma"` resolves; `type: module`; built with `tsup`.
- Deps: `@prisma/generator-helper` (protocol), `@prisma/internals` (programmatic sub-generator run, or spawn fallback). Bundle `@ghentcdh/crouton-codegen` + `@ghentcdh/crouton-core` logic (`tsup` `noExternal`) since codegen is private.
- `zod-prisma-types` + `prisma`/`@prisma/client` are **peer deps** expected in the consumer.

### `src/generator.ts` (the bin)

`generatorHandler({ onManifest, onGenerate })`:
- `onManifest`: `prettyName: "Crouton"`, `defaultOutput`, `requiresGenerators: []`, declare accepted config keys (`clientOutput`, `zodOutput`, `previewFeatures`, plus zod passthrough flags).
- `onGenerate(options)` — order `normalize → zod → custom` (crouton does **not** run the client; that block runs on its own):
  1. **Normalize (first).** Apply `normalize-schema.json` relation-field renames to the schema SDL string. Write the normalized SDL back to the real `schema.prisma` so source, the client block, and zod all converge (see Caveat).
  2. **Run zod.** Build a temp schema in `os.tmpdir()` = datasource block + **normalized** datamodel + a synthesized `zod` block only (output from `zodOutput`), **without** any crouton or client block (avoids self-recursion and double client emit). Run via `@prisma/internals` `getGenerators()` (recommended) or by spawning `prisma generate --schema <tmp>` limited to the zod generator. Resolve `zodOutput` to an absolute path against the real schema dir.
  3. **Post-generate custom (no-prompt only).** `fixZodImports(zodOutput)` + zod barrel/import cleanup, then `buildEnumRegistry(dmmfToDbModels(...))` → write enum registry, and any other deterministic emit. No resource.json / schema.ts here.

### Reuse, don't fork
Import `dmmfToDbModels`, `fixZodImports`, `buildEnumRegistry`, etc. from `crouton-codegen` and bundle them, so the generator and the CLI share one implementation.

### Caveat: client vs. zod consistency under a single-pass `prisma generate`
Because the `client` block stays separate, Prisma parses the datamodel once and generates the client from the **pre-normalize** DMMF, while crouton generates zod from the **normalized** temp schema. If the on-disk schema still holds ugly relation names, the runtime client API and the zod types disagree.

Recommended reconciliation (keeps decisions #1 + #2 both true):
- The CLI pull pipeline keeps applying `normalizeSchema` **right after `db pull`, before `generate`**, so the schema on disk is already normalized before any generate pass → client + zod agree.
- crouton's in-pass normalize (step 1) then acts as a defensive no-op on an already-normalized schema, and still guarantees clean zod output for a bare `prisma generate` run (e.g. after a hand edit). It also writes the normalized SDL back, so the next client generate converges.

Net: `normalizeSchema` lives in **both** places — a schema-text transform in the pull pipeline (feeds the client) and inside the generator (feeds zod + self-heals). If you'd rather it live in exactly one place, the alternative is letting crouton own the client block too (reopens decision #2).

## CLI / path changes

1. **`datasource-scaffold.ts` (`buildDatasourceFiles`, prisma branch)** — keep the `generator client` block; replace the `zod` block with a `generator crouton` block carrying `zodOutput` (+ any zod passthrough flags). `datasource db { ... }` unchanged (url still via `prisma.config.ts`).
2. **`data-source.json`** — keep `zodOutput` / `clientOutput` / `generatedTypesImport` (still needed for the resource `schema.ts` import and the runtime client import in datasource `index.ts`); they must equal the generator's configured outputs. No new field strictly required.
3. **`prisma-shell.ts` `pullAndGenerate`** — becomes `backup → dbPull → caseFormat → normalizeSchema → prismaGenerate`. **Keep** `normalizeSchema` here (it must run before the client block is generated — see Caveat), but **drop** the CLI-side `fixZodImports` + `zodOutputDir` plumbing, since crouton now owns zod post-processing. `prismaGenerate` now triggers both the client and the crouton generator.
4. **`update/runner.ts`** — remove the `zodDir` / `fixZodImports` / `zodImportsFixed` handling that `pullAndGenerate` no longer performs; keep the `prisma generate` invocation (it now triggers crouton). Adjust the generate-only branch likewise.
5. **`create-crouton` / `add-crouton` `deps.ts`** — add `@ghentcdh/crouton-prisma` (+ ensure `zod-prisma-types`, `prisma`, `@prisma/client`) to scaffolded consumer deps.
6. **Migration** — for existing datasources, a `crouton migrate-schema` codemod (or a note in `update`) that rewrites the two blocks into the single crouton block, reading old `output` paths into `clientOutput` / `zodOutput`.

## Risks
- **Self-recursion** if the temp schema still contains the crouton block — must be stripped.
- **Prisma/zod version coupling** if using `@prisma/internals` `getGenerators`; spawning the zod bin against the temp schema is the more decoupled fallback.
- **Ordering** of field-rename normalize vs. zod (decision #1) — getting this wrong silently reintroduces ugly relation names in zod output.
- **Bundling** private `crouton-codegen`/`crouton-core` into the published generator (peer/external boundaries).

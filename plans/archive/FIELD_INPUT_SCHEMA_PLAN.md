Status: implemented
# Field Input Schema Plan

Make `fieldInput` type-safe per control type, self-describing via a per-type
`$schema`, and **autogenerated** from a single Zod source of truth in
`crouton-core` — with a drift-check guard tying each schema to its Vue
renderer, and a first-class escape hatch for custom controls. Foundation for a
future form builder.

## 1. Motivation

Today `fieldInput` is one loose Zod object (`FieldInput.schema.ts`):

```ts
export const FieldInputSchema = z.object({
  type: z.string().optional(),
  format: z.string().optional(),
  resource: z.string().optional(),
  relationType: RelationType.optional(),
  // ...
  options: z.union([RelationFieldInputOptionsSchema, z.unknown()]).optional(),
});
```

Consequences:

- `options` is effectively `unknown` for every control except relation, so
  authoring an autocomplete/select/date/toggle field gets no validation and no
  editor autocomplete.
- The real per-type option shapes already exist — but as **TypeScript
  interfaces** in `control.builder.ts` (`AutocompleteOptions`, `SelectOptions`,
  `ToggleOptions`, `DateOptions`, `DateRangeOptions`, `MarkdownOptions`,
  `TextAreaOptions`, `DetailOptions`). They are not Zod, so they can't validate
  JSON, can't emit JSON Schema, and can drift from the Vue renderers that
  actually consume them.
- There is no per-type `$schema` an author can point an editor at.

Goal shape (author-facing, **options stays nested** — existing resource.json
files keep working):

```jsonc
"fieldInput": {
  "$schema": "https://ghentcdh.github.io/crouton/schema/v1/autocomplete.schema.json",
  "type": "autocomplete",
  "options": {
    "resource": "./author/resource.json",
    "labelKey": "name",
    "valueKey": "id",
    "storeValue": true
  }
}
```

## 2. Decisions (locked)

1. **Nested `options`.** Keep `fieldInput.options` as-is. No migration of
   existing files; the per-type schema constrains what goes *inside* `options`.
2. **Single source of truth = Zod in `crouton-core`.** One schema per control
   type. `z.toJSONSchema` emits the per-type JSON Schema files, reusing the
   existing `gen-resource-schema.mjs` machinery.
3. **Drift-check guard.** A unit test asserts each Vue renderer's declared
   props/options line up with its Zod schema, so a renderer and its schema
   can't diverge silently. Zod stays the thing codegen reads — we do **not**
   reflect Vue runtime props into JSON Schema.
4. **Custom escape hatch.** `type: "custom"` (or a `customRender` set) accepts
   an open `options` bag so an app with its own controller/renderer is never
   blocked by the registry.

## 3. Current state (map of what's involved)

| Concern | Location |
| --- | --- |
| Loose field schema | `crouton-core/src/lib/resource/FieldInput.schema.ts` |
| Field variant fallback (input/view/table) | `crouton-core/src/lib/resource/fieldVariants.ts` |
| Column schema wiring `fieldInput` | `crouton-core/src/lib/resource/Column.ts` |
| Typed option interfaces (to port to Zod) | `crouton-core/src/lib/layout/control.builder.ts` (`ControlType`, `*Options`) |
| Vue renderers + bindings | `crouton-forms-vue/src/forms/renderers/controls/*` (`AutocompleteControlRenderer.vue`, `useSelectBinding.ts`, `registry.ts`) |
| resource.schema.json generator | `crouton-core/scripts/gen-resource-schema.mjs` (`z.toJSONSchema`, draft-7, `io:'input'`) |
| Versioned schema URL + `$schema` stamping | `crouton-codegen/src/serialize.ts` (`RESOURCE_SCHEMA_URL`), `crouton-core/src/lib/resource/version.ts` (`CURRENT_RESOURCE_VERSION = 1`) |
| Per-kind refinement (relation/autocomplete already special-cased) | `ResourceJson.schema.ts` `refineByKind` |

Notable: `control.builder.ts` already models autocomplete as a **union** of
three shapes — inline `options[]`, remote `uri`, and `resource` — plus
`freeText`/`enableCreate`. Relation is special (references another
`resource.json`, cardinality, FK). The Zod port must preserve both.

## 4. Target architecture

### 4.1 A field-input registry in `crouton-core`

New folder `crouton-core/src/lib/resource/field-input/`:

```
field-input/
  base.options.ts          # shared ControlOption keys as Zod (label, hideLabel,
                            #   placeholder, readonly, colspan, width/styles, customRender…)
  types/
    string.options.ts
    number.options.ts
    textarea.options.ts
    markdown.options.ts
    boolean.options.ts
    toggle.options.ts
    select.options.ts       # select + multiselect
    autocomplete.options.ts # union: inline | remote(uri) | resource
    date.options.ts         # date + dateTime
    date-range.options.ts
    relation.options.ts     # references RelationFieldInputOptionsSchema (moved here)
    array.options.ts        # detail/array layout
    custom.options.ts       # open bag (.catchall(unknown))
  registry.ts              # Map<ControlType, { options: ZodType, meta }>
  field-input.schema.ts    # discriminated-by-`type` builder over the registry
  index.ts
```

Each `*.options.ts` is a `z.object(...).catchall(z.unknown())` (stay permissive
for forward-compat — unknown keys allowed but known keys typed), carrying
`.describe()` text lifted from the existing JSDoc so editor tooltips survive.

`registry.ts`:

```ts
export const fieldInputRegistry = new Map<string, FieldInputTypeDef>([
  ['autocomplete', { options: AutocompleteOptionsSchema, schemaFile: 'autocomplete' }],
  ['select',       { options: SelectOptionsSchema,       schemaFile: 'select' }],
  ['relation',     { options: RelationFieldInputOptionsSchema, schemaFile: 'relation' }],
  // ...
  ['custom',       { options: CustomOptionsSchema,        schemaFile: 'custom' }],
]);
```

### 4.2 `FieldInput.schema.ts` becomes a discriminated builder

`fieldInput` keeps its top-level keys (`type`, `format`, `resource`,
`relationType`, `foreignKey`, `position`, `defaultValue`, `detail`, …) but
`options` is resolved **per `type`** from the registry:

```ts
const buildFieldInputSchema = () =>
  z.discriminatedUnion('type', [...registry entries...])
   .or(LooseFieldInputSchema);   // fallback: unknown type => today's loose behavior
```

- Known `type` → `options` validated by that type's schema.
- Unknown `type` or `type: 'custom'` → open `options` (no regression, custom
  controllers keep working).
- `$schema` is accepted and ignored by the loader (it's an editor hint); it is
  *stamped* on write (§4.4), like `resource.json`'s own `$schema`.
- `FieldVariantSchema` (view/table overrides) reuses the same per-type option
  shapes so `mergeFieldVariant` still deep-merges one level into `options`.

Because `z.toJSONSchema` rejects some constructs (as the codebase already knows
— see `refineByKind`'s note and the `try/catch` in `generateResourceJsonSchema`),
the discriminated union is emitted per-type as standalone files (§4.3) and the
**embedded** copy inside `resource.schema.json` stays permissive
(`options: {}`), exactly as it is today. Editors get precise validation via the
per-type `$schema`; the master schema stays generatable.

### 4.3 Codegen: per-type JSON Schema files

Extend `gen-resource-schema.mjs` (or a sibling `gen-field-schemas.mjs` invoked
from the same tsup `onSuccess`) to iterate the registry:

```js
for (const [type, def] of fieldInputRegistry) {
  const schema = z.toJSONSchema(def.options, {
    target: 'draft-7', io: 'input', unrepresentable: 'any',
  });
  schema.$id = `${BASE}/schema/v${CURRENT_RESOURCE_VERSION}/${def.schemaFile}.schema.json`;
  // write to: dist/, src committed copy (drift-guarded), docs/.vuepress/public/schema/v<N>/
}
```

Reuses the existing three-location write + versioned snapshot
(`<file>.v<N>.json`) + docs publishing already in `gen-resource-schema.mjs`, so
the files are served at the URLs the `$schema` values point to.

Add these committed files to the CI drift check that already guards
`resource.schema.json`.

### 4.4 Stamping `$schema` on write

In `crouton-codegen/src/serialize.ts`, when serializing a resource.json, stamp
each column's `fieldInput.$schema` (and `fieldView`/`fieldTable`) from the
registry keyed on `type`, the same way `withResourceHeader` stamps the top-level
`$schema`/`schemaVersion`. Idempotent + diff-friendly (drop existing, re-add at
front). Unknown/custom types get no stamp (or a `custom.schema.json` pointer).

### 4.5 Drift-check guard (the option-3 piece)

A vitest in `crouton-forms-vue` (it can import both the renderers and the core
schemas) that, for each entry in the renderer `registry.ts`:

- reads the option keys the renderer/binding actually consumes — the
  `useSelectInput('options','labelKey','valueKey',…)` field lists in
  `useSelectBinding.ts` are already explicit allowlists; expose them as exported
  const arrays so the test can read them, or read the control's
  `*.properties.ts` prop keys;
- compares that set against `keys(fieldInputRegistry.get(type).options.shape)`;
- **fails** if a renderer consumes an option the schema doesn't define, or the
  schema defines a *required* option the renderer ignores. Unknown-but-optional
  is tolerated (both sides stay permissive).

This is the "derived from render properties" guarantee without generating from
Vue runtime props: Zod stays canonical, the test keeps them honest.

### 4.6 Custom controllers

- `type: 'custom'` + `customRender: '<component key>'` → `CustomOptionsSchema`
  (`z.object({ customRender: z.string().optional() }).catchall(z.unknown())`).
- Apps register their renderer in the Vue `registry.ts` and, optionally, their
  own options Zod via a public `registerFieldInputType(type, optionsSchema)` —
  mirroring the existing `getResourceExtensions()` extension registry pattern —
  so a custom type can also emit its own `$schema` from the app build
  (`generateResourceJsonSchema()` already shows the "app registers, then emits
  its own schema" precedent).

## 5. Form builder (future, non-blocking)

The registry makes a form builder mostly declarative:

- Each `FieldInputTypeDef` gains UI metadata: `label`, `icon`, `group`,
  `supports: { multi, remote, options }`, and a JSON-Schema-driven options
  editor (the per-type `*.schema.json` *is* the config form for that control).
- A builder palette = `[...fieldInputRegistry.values()]`; dropping a field
  writes a `fieldInput` block whose `options` form is generated from that type's
  schema (crouton already renders JSON Schema → form, so the builder eats its
  own dog food).
- Relation/autocomplete stay special (they need a resource picker), flagged via
  `def.needsResource`.

Out of scope for this plan beyond making the registry shape support it.

## 6. Phased implementation

**Phase 1 — Zod source of truth (core, no behavior change)**
1. Port `control.builder.ts` `*Options` interfaces to Zod under
   `field-input/types/*`, carrying JSDoc into `.describe()`.
2. Move `RelationFieldInputOptionsSchema` into `relation.options.ts`.
3. Build `registry.ts` + `field-input.schema.ts` (discriminated union `.or`
   loose fallback). Keep `control.builder.ts` interfaces as
   `z.infer` re-exports so `crouton-forms-vue` types are unchanged.
4. Wire `FieldInputSchema`/`FieldVariantSchema` to the new builder; verify
   `mergeFieldVariant` + `fieldVariants.ts` still pass existing specs
   (`fieldVariants.test.ts`).

**Phase 2 — Codegen + `$schema`**
5. Extend the gen script to emit per-type `*.schema.json` (dist + committed +
   docs), versioned; add to CI drift check.
6. Stamp `fieldInput.$schema` in `serialize.ts`.
7. Regenerate example resource.json files (`examples/book-collection`) and
   confirm minimal diffs.

**Phase 3 — Drift guard + custom**
8. Export the renderer option allowlists; add the drift-check vitest.
9. Add `registerFieldInputType` + document the custom path.

**Phase 4 — polish**
10. Docs page under `docs/` describing field types + linking each `$schema`.
11. (Later) form-builder metadata on the registry.

## 7. Backward compatibility & risks

- **No file migration**: nested `options` preserved; `CURRENT_RESOURCE_VERSION`
  stays 1 (this is additive validation, not a shape change). Bump only if we
  ever tighten `options` from permissive to closed.
- **`z.toJSONSchema` limits**: mitigated by keeping the embedded schema
  permissive and shipping precise per-type files (same trade-off already made
  for the master schema).
- **Autocomplete is a union** (inline/remote/resource) — the JSON Schema will be
  a `oneOf`; verify editor (VS Code) autocomplete behaves acceptably on `oneOf`.
- **Drift test brittleness**: keep it "consumes ⊆ schema (+ required ⊆
  consumed)" rather than exact equality, so adding an optional prop on one side
  doesn't red-fail unrelated work.
- **Custom types**: never validated against a closed schema — intentional.

## 8. Open questions

- Emit one combined `field-input.schema.json` (`oneOf` over all types, keyed by
  `type`) in addition to per-type files, so an author can point `$schema` at a
  single URL and still get per-type narrowing? (Nice for the editor; more to
  generate.)
- Should `format` (legacy) and `type` be unified? Several controls key off
  `options.format` in `control.builder.ts` while `fieldInput.type` also exists —
  worth reconciling before the builder leans on `type` as the discriminant.
- Drift source: exported allowlist arrays vs reading `*.properties.ts` prop
  keys — allowlists are simpler and already exist in the bindings.
